## 1 需求与旧模型问题

### 1.1 需求

原来一条 `treatmentLog_t` = 患者信息（用户ID/姓名/年龄/性别）+ 一次治疗参数（激光功率/已发射能量/发射时间/波长/预设方案）混在一起，一次治疗存一条。现在要求：**一位患者对应多条治疗病历**，例如患者 A 做 5 次治疗，5 组参数都要留档，且能按患者查看。先按每位患者最多 10 条评估。

### 1.2 旧模型（改造前）

`MainApp/treatment.h` 中旧结构（armcc 实测 **36 B**）：

| 偏移 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| 0 | id | uint16 | 病历序号，等于数组下标 |
| 2 | age | uint8 | 年龄 |
| 3 | gender | uint8 | 性别 |
| 4 | laserPower | int16 | 功率 W |
| 6 | releaseEnergy | int32 | 累计能量 J |
| 10 | releaseTime | int32 | 累计时间 s |
| 14 | name[16] | char | 姓名 |
| 30 | laserWave | uint8 | 波长 |
| 31 | protocol | uint8 | 预设方案 |
| 32 | （填充） | — | 对齐到 36 B |

存在的问题：

1. **患者信息重复**：同一患者做 10 次治疗，姓名/年龄/性别/ID 要写 10 遍，49152 B 只能存 1365 条。
2. **没有"患者"这一层**：无法按患者聚合查询、无法显示"该患者第 n/N 条"。
3. **修改靠整表搬家**：插入/删除要把后面所有记录逐条前移，`id` 由下标推导。
4. **空槽判据与擦除值不一致**（历史隐患）：代码把 `id == 0xFFFF` 当空槽，而 `sPlcPort/sPlcEprom.c` 的 `clearEprom(CLEAR_EPROM_TREATMENT)` 把整区写成 **0x00**，清空后重上电会读到一串 `id = 0` 的"幽灵病历"。新模型把 `patientId == 0` 与 `0xFFFF` **都判为空块**，有效 ID 从 1 起，从根上规避。
5. **枚举直接落盘**：AC5 枚举 1 B、AC6 默认 4 B，换编译器结构体尺寸变化，存量数据解析错位。

## 2 新数据模型

### 2.1 三层结构

```
FRAM 病历区（55708 B，8548~64255）
├── 患者块 #0 ── 144 B ─┐
│   ├ 患者头 24 B      │  姓名19 + patientId2 + age1 + gender1 + recordCount1（无填充）
│   └ 病历数组 10×12B  │  索引 0 = 最早一次治疗
├── 患者块 #1 ── 144 B ─┤  …… 块与块定长相邻，无碎片
├── …                    │
└── 患者块 #385 ────────┘  共 386 块（55584 B），尾部余 124 B
```

RAM 中另有一个**会话结构** `treatmentLog_t`（40 B，不落盘），表示"当前这次治疗还没归档的数据"：

- `patientId = 0` → 新患者，保存时自动分配 ID；
- `patientId != 0` → 复诊，保存时追加到该患者。

> `treatmentLog_t` 保留全部旧字段名（`id` 换成 `patientId`，其余 `name/age/gender/laserPower/releaseEnergy/releaseTime/laserWave/protocol` 不变），HMI 里原来的赋值语句**一行都不用改**。

### 2.2 落盘字节布局（编译器无关的格式契约）

> 下列偏移不是"某编译器 sizeof 出来的结果"，而是**写死在代码里的字节契约**（`CONFIG_EPROM_TREATMENT_OFF_*` / `REC_OFF_*` 常量）。FRAM 里的字节由 `treatment.c` 的小端编解码函数生成，结构体只在 RAM 里用，因此任何编译器的对齐/填充/枚举宽度都不会改变这些字节。

**一条病历 = 12 B（小端）**

| 偏移 | 字段 | 类型 | 单位/说明 |
| --- | --- | --- | --- |
| 0 | releaseEnergy | int32 | 已发射能量 J |
| 4 | releaseTime | int32 | 发射时间 s |
| 8 | laserPower | int16 | 激光功率 W |
| 10 | laserWave | uint8 | 波长（`LASER_WAVE_ENUM` 取值） |
| 11 | protocol | uint8 | 预设方案（`PROTOCOL_ENUM` 取值） |

**一个患者档案块 = 144 B（块头 24 B 无填充）**

| 偏移 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| 0..18 | name[19] | char | 姓名，未用字节填 0（由 16 扩到 19，吃掉原 reserved + 2 B 对齐填充） |
| 19..20 | patientId | uint16 小端 | 1 ~ 0xFFFE 有效；0 / 0xFFFF = 空块 |
| 21 | age | uint8 | 年龄 |
| 22 | gender | uint8 | 性别（`MALE=1 / FEMALE=2`） |
| 23 | recordCount | uint8 | 已保存病历条数 0~10 |
| 24..143 | record[10] | 10 × 12 B | 索引 0 为最早一次治疗，起点仍 4 字节对齐 |

落盘字段全部是显式定宽整数（`uint8_t / int16_t / int32_t`），不落枚举；时间/能量按小端逐字节拼装（`treatmentPutU32/treatmentGetU32`），不依赖编译器端序。
> 注意：本次把姓名从 16 B 扩到 19 B，**块头字段偏移全部改变**（id 16→19、age 18→21、gender 19→22、count 20→23），属于破坏性格式变更；按既有约定**升级后整片 EPROM 清除**，不做数据迁移。块大小仍 144 B，容量（386 患者）不变。

### 2.3 容量宏

| 宏 | 值（G5） | 说明 |
| --- | --- | --- |
| `CONFIG_EPROM_TREATMENT_RECORDS_PER_PATIENT` | 10 | 每人病历槽位数（决定块大小 144 B） |
| `CONFIG_EPROM_TREATMENT_OVERWRITE_OLDEST` | 0 | 满 10 条策略：0 = 拒绝保存，1 = 前移覆盖最旧 |
| `CONFIG_EPROM_TREATMENT_RECORD_BYTES` | 12 | 单条病历落盘字节数（**纯常量**） |
| `CONFIG_EPROM_TREATMENT_NAME_BYTES` | 19 | 姓名落盘字节数（16→19，填满块头） |
| `CONFIG_EPROM_TREATMENT_HEAD_BYTES` | 24 | 患者块头落盘字节数（**纯常量**，19+2+1+1+1=24 无填充） |
| `CONFIG_EPROM_TREATMENT_PATIENT_BYTES` | 144 | `24 + N × 12`，纯算术表达式 |
| `CONFIG_EPROM_TREATMENT_RECORD_SIZE` | 12 | 旧名兼容别名（= `RECORD_BYTES`，不再是 `sizeof`） |
| `CONFIG_EPROM_TREATMENT_PATIENT_SIZE` | 144 | 旧名兼容别名（= `PATIENT_BYTES`，不再是 `sizeof`） |
| `CONFIG_EPROM_TREATMENT_PATIENT_MAX` | 386 | `病历区 / 144`，纯整数除法，与编译器无关 |
| `CONFIG_EPROM_TREATMENT_RECORD_MAX` | 3860 | `386 × 10` |
| `CONFIG_EPROM_TREATMENT_PATIENT_EMPTY` | 0xFFFF | 空块标记 |
| `CONFIG_EPROM_TREATMENT_PATIENT_ID_MIN/MAX` | 1 / 0xFFFE | 有效 ID 范围 |

### 2.4 应用级边界（本次新增）

```c
CONFIG_EPROM_TREATMENT_PATIENT_LIMIT    // 病历人数上限，默认 = PATIENT_MAX(386)
CONFIG_EPROM_TREATMENT_RECORD_LIMIT     // 每人病历条数上限，默认 = RECORDS_PER_PATIENT(10)
```

- 两个宏可在板型 `AppConfig.h` 里覆盖，用于"产品限流/临时收缩"，不需要改数据模型。
- 读取接口：`treatmentEpromPatientLimit()`、`treatmentEpromRecordLimit()`；超过物理容量/槽位数时**自动钳位**，不会越界寻址。
- 三个写入入口统一按上限拦截：

| 入口 | 判断 | 超限返回 |
| --- | --- | --- |
| `treatmentEpromPatientAdd` | `PatientCount() >= PatientLimit()` | `ERR_FULL` |
| `treatmentEpromRecordAdd` | `该患者条数 >= RecordLimit()` | `ERR_FULL`（策略=1 时改为前移覆盖） |
| `treatmentEpromRecordInsert` | `该患者条数 >= RecordLimit()` | `ERR_FULL` |
| `treatmentEpromSaveSession` | 走上面 `PatientAdd + RecordAdd`，同样受限 | `ERR_FULL` |

> 边界宏现在是**纯整数表达式**（`PATIENT_MAX` 由 `PATIENT_BYTES` 常量算出，不再含 `sizeof`），所以既能在 `#if` 里做编译期自检（配置越界直接 `#error`），运行时的 `treatmentEpromPatientLimit()/RecordLimit()` 又保留钳位作为二重兜底。

### 2.5 编译器无关性（本次新增，实测三套编译器）

改造前，容量与布局有 3 个隐蔽的编译器依赖，任何一个变了都会让"同一片 FRAM、同一个起始地址"存出不同的患者数：

| 依赖点 | 改造前 | 改造后 |
| --- | --- | --- |
| 块大小/容量 | `sizeof(treatmentPatient_t)` | 常量 `PATIENT_BYTES = 24 + N*12` |
| 病历数组偏移 | `(uint8_t*)&((T*)0)->record - 0`（随 padding 变） | 常量 `OFF_RECORD = 24` |
| FRAM 读写 | 结构体指针直接 memcpy（随端序/打包变） | 显式小端编解码 `PutU16/PutU32` |

实测（同一份 `treatment.h`，同一组分区宏，只换编译器）：

| 量 | AC5 (armcc 5.06u6) | AC6 (armclang) | GCC 11.2 (`-mcpu=cortex-m4`) | GCC + `-fpack-struct=1` |
| --- | --- | --- | --- | --- |
| 病历区字节数 | 55708 | 55708 | 55708 | 55708 |
| 可存患者 | **386** | **386** | **386** | **386** |
| 可存病历 | 3860 | 3860 | 3860 | 3860 |
| `sizeof(treatmentRecord_t)` | 12 | 12 | 12 | 12 |
| `sizeof(treatmentPatient_t)` | 144 | 144 | 144 | **144**（字段重排后打包也无空隙） |
| `offsetof(record)` | 24 | 24 | 24 | **24** |
| 落盘患者块字节 `PATIENT_BYTES` | **144** | **144** | **144** | **144** |

结论：即使加 `-fpack-struct=1` 强制打包，RAM 结构体也是 144 B、偏移 24；落盘块恒定 144 B、患者数恒定 **386**——容量、地址、字节格式三者都已与编译器解耦。

### 2.6 为什么不改成链表（评估结论：不采用）

| 方案 | 每位患者成本（k = 实际条数） | 有无指针 |
| --- | --- | --- |
| 定长块（当前实现） | 恒定 144 B | 无 |
| 链表（患者头 first 指针 + 每节点 next） | 24 + 14 k（病历 12 B + 2 B 16 位偏移指针） | 有 |
| 无指针变长块（备选） | 24 + 12 k（头里记实际条数，整块紧凑） | 无 |

链表的真实代价：

1. **每条病历 +2 B 指针**（64 KB FRAM 内只能用 16 位偏移；用 C 原生 32 位指针是 +4 B），节点 12→14 B，开销 +16.7%；
2. 必须再维护一条**全局空闲节点链**，否则删除病历后节点无法回收——这是额外的持久化数据结构和掉电风险点；
3. 指针写入中途掉电会**断链/环链**，直接破坏现有"先数据、后计数"的掉电安全模型；
4. 无法再用 `START + i*144 + 24 + r*12` 做 O(1) 定位，HMI 扁平浏览、CSV 导出、`FlatLocate` 全部要改成串行跟链。

量化（55708 B 病历区）：

| 场景 | 定长块 | 链表 | 无指针变长块 |
| --- | --- | --- | --- |
| 盈亏平衡 | — | 平均 k = **8.57 条**才追平定长块 | k=10 时与定长块相等 |
| 全员 10 条（最坏） | **386 患者** | 339 患者（**少 47**） | 386 |
| 平均 3 条 | 386 | 844 | **928**（比链表多 84，省在没有指针） |
| 平均 1 条 | 386 | 1213 | **1547** |

RAM 方面链表**不省**：当前实现本来就不把整表放 RAM，读一条丢一条；链表反而要带 free list 管理代码（Code 增加）。

> **结论：不采用链表。** 若以后实机数据证明"低条数患者占多数、10 槽预留确实浪费"，正确的替代是**无指针变长块**——块头记实际条数，块大小 = 24 + n×12，增删时整块重排（FRAM 无擦写寿命，最多写 144 B），既拿到按需空间，又不引入任何指针和断链风险。

另加两道编译期护栏：

- 结构体"装得进去"断言：`sizeof(treatmentRecord_t) <= 12`、`sizeof(treatmentPatient_t) <= 144`，超了直接编译失败（防止有人加字段后栈帧/对齐失控）；
- 格式自检 `#if`：病历数组偏移必须等于块头字节数且 4 字节对齐、病历字段偏移必须填满 12 B、头部字段不得越界、每人条数不得超 255（`recordCount` 只有 1 字节）。

> 说明：AC6 目前无法直接编译整个工程（工程头链 `lib/compiler.h` 明确只接受 ARM Compiler 5/6 且存在 AC5 专用写法），所以上面的 AC6/GCC 数据是用"空壳 `sPlc.h` + 命令行注入分区宏"把 `treatment.h` 的布局部分单独隔离出来编译验证的；这恰好也证明了**布局契约本身不依赖工程其它头**。

## 3 存储容量核算与分区

### 3.1 计算口径

```
患者块大小 = 24 B（头，字段紧凑无填充） + N × 12 B（N = 每人病历条数）
可存患者数 = floor(病历区字节数 / 患者块大小)
可存病历数 = 可存患者数 × N
```

### 3.2 G5 分区全表（把 DM 缩到 128 字后，实测）

| 分区 | 起 | 止 | 字节 | 说明 |
| --- | --- | --- | --- | --- |
| MR NVRAM | 0 | 63 | 64 | 32 字 × 2 |
| DM NVRAM | 64 | 319 | 256 | 128 字 × 2（用户由 512 字缩容，让出 768 B） |
| FD（方案存档） | 320 | 4415 | 4096 | 2048 字 × 2 |
| BK（BKSRAM 映射） | 4416 | 8511 | 4096 | 1024 字 × 4 |
| 分区 CRC 链 | 8512 | 8547 | 36 | 9 个 CRC32（MR/DM/FD/BK/MCU_FW/LCD_FW/TREATMENT/CFG/LOG） |
| **病历区（已扩满）** | **8548** | **64255** | **55708** | 起点 = `BK_END + 37`；原 15104 起 → 9316 起 → 8548 起，累计扩了 6556 B |
| 配置区 | 64256 | 65279 | 1024 | deviceConfig |
| LOGINFO | 65280 | 65535 | 256 | 记录信息 |
| **合计** | 0 | 65535 | **65536** | 全片无空洞 |

容量：`55708 / 144 = 386.86` → **386 位患者**（占用 55584 B），尾部余 **124 B**（不足一个 144 B 块，无法再利用）。
空间利用率 **99.78%**。

### 3.3 全部板型对比（容量口径不同，其它板未改分区）

| 板型 | 病历区 | 芯片 | 旧模型条数(36B) | **新模型患者(144B)** | 新模型病历数 |
| --- | --- | --- | --- | --- | --- |
| G5_TRI_A1_20260915 | **55708 B（已扩满）** | MB85RS512 64 KB | 1547（原 49152 B 时 1365） | **386** | 3860 |
| 6M3S_JL_FC | 26816 B | MB85RS2MAT 32 KB | 744 | **186** | 1860 |
| LYPE_2V0_M450 | 26826 B | FM25W256G 32 KB | 745 | **186** | 1860 |

其它板型可用同一表达式扩满（逻辑一致）：把 `CONFIG_EPROM_TREATMENT_START` 改成 `(CONFIG_EPROM_BK_END + 37L)` 即可，但**需先确认该板 BK 分区与 CRC 链布局相同**。

### 3.4 不同块结构的取舍（按 55708 B 计算）

| 方案 | 块大小 | 患者数 | 病历总数 |
| --- | --- | --- | --- |
| 只有 12 B 病历参数（**当前实现**） | 144 B | **386** | 3860 |
| 每条病历 + 4 B 日期时间戳 | 184 B | 302 | 3020 |
| 12 B 病历 + 块尾 4 B CRC | 148 B | 376 | 3760 |
| 12 B + 时间戳 + CRC | 188 B | 296 | 2960 |

> 目前**不加时间戳**：需求只列了功率/能量/时间/波长/方案 5 项，时间戳会让患者数掉到 302。若后续要"按日期查病历"再加，接口不变。

### 3.5 空闲空间盘点（两次扩容的关键判断）

改造前，9316~15103 这段 **5788 B 完全没有分区使用**（旧代码把病历区固定成 `32*1536`，从 15104 起）。这段空间上方是 CRC 链、下方是旧病历区起点，因此：

- **病历区可下探的极限 = `BK_END + 37`**（再往前就越过 CRC 链、踩到 BK 分区，`BoardConfig.h` 自带 `#if (CONFIG_EPROM_BK_END >= CONFIG_EPROM_MR_CRC)` 会直接 `#error`）；
- 第一次把起点从 15104 挪到 9316，**5788 B 并入病历区**（341 → 381 位患者）；
- 第二次靠 **DM 从 512 字缩到 128 字**（`CONFIG_DM_SIZE * 2` = 1024 B → 256 B），FD/BK/CRC 链整体前移 768 B，起点再挪到 **8548**，病历区 54940 → **55708 B**（381 → **386** 位患者，尾部余 124 B）。

> 注意两点：
> ① `CONFIG_EM_SIZE` 512→320 **不增加 EPROM 病历区**——EM（非保持数据寄存器）不落 EPROM，这次 EM 缩容只省 SRAM（NVRAM0/NVRAM1 各 384 B）；真正让出 EPROM 的只有 DM 的 768 B。
> ② 分区一旦变动，旧片子里的病历数据位置全部失效，按既有约定**升级后整片 EPROM 清除**，不做数据迁移。
> ③ DM 缩到 128 字意味着 DM 索引只能用 0~127；FD 缩容/前移后写回地址也随宏推导，**须实机跑一遍 DM 掉电保存与 FD 方案存取**（见 §10）。

### 3.6 RAM 实测（DM/EM 缩容后全量重编）

| 项目 | 数值 | 说明 |
| --- | --- | --- |
| `sizeof(treatmentLog_t)` | 40 B | 会话结构，静态变量；与患者数/条数无关（姓名扩到 19 后由 36 变 40） |
| 患者块局部变量 | 144 B | `PatientGet/Add/Delete/Traverse` 的栈帧 |
| 编解码缓冲 | +12 B（+12 B 头部） | `treatmentPatientToBytes` 再带一块 144 B 缓冲，峰值约 300 B |
| `NVRAM0` / `NVRAM1` | 各 **1840 B**（920 字 × 2） | `CONFIG_NVRAM_SIZE = TMP_END+1`，随 DM/EM 自动缩；缩容前各 2992 B |
| CSV 静态缓冲 | 2528 B | `minicsvApp.c` 的 `csv_col_buf[10][48]`；**当前被链接器整段移除**（见 §3.7） |
| FreeRTOS 堆 | 40960 B | `ucHeap`（heap_4，静态 ZI） |
| mainApp 任务栈 | 24576 B | 从上面的堆里分配，144 B 栈帧约占 0.6% |
| 启动栈 / C 堆 | 6144 B / 4096 B | `startup_stm32f405xx.s` |

**实测构建（0 Error / 2 Warning）**：`Code=195752 RO-data=8552 RW-data=1548 ZI-data=108492`，`Total RW Size = 110040`。

**RAM 余量**：

| 区域 | 已用 | 上限 | 余量 |
| --- | --- | --- | --- |
| RW_IRAM1（0x20000000） | 97752 B | 114688 B（112 KB） | **16936 B** |
| RW_IRAM2（0x2001C000） | 0 B | 16384 B（16 KB） | **16384 B（整块闲置）** |

即 128 KB SRAM 用了约 107.5 KB，**还剩约 33 KB**（IRAM1 16.9 KB 连续可用 + IRAM2 整 16 KB 未启用）。

### 3.7 需不需要动态分配内存（结论：不需要）

| 判断依据 | 事实 |
| --- | --- |
| 病历是否需要常驻 RAM | 不需要。386 位患者 × 144 B = 55.3 KB，本来就不可能在 RAM 全缓存；实现是**按需读一条 12 B 病历**，用完即丢 |
| RAM 占用是否随容量增长 | 不增长。患者数、每人条数只影响 FRAM 地址计算，占用的栈帧恒定 144/12 B |
| 现有余量 | 33 KB 空闲，最坏路径（翻页 + 删除 + 保存）栈深 < 500 B |
| 动态分配的代价 | ① `malloc` 失败时病历保存会失败，激光治疗已结束却存不下，属不可接受的功能性失败；② heap_4 也是**静态 ZI 池**（`ucHeap` 40 KB），只是把固定占用换了个名字，并没有真"省"；③ 长时间运行碎片化、与实时任务抢堆，排查成本高 |

结论：**保持纯静态 + 栈上定长块**。真正要回收 RAM 时优先级是：`minicsvApp` 的 2528 B 静态缓冲（当前本就未被链接）、`ucHeap` 40 KB 里给 mainApp 的 24 KB 是否偏大、以及把 IRAM2 的 16 KB 用起来（需改 scatter/sct）。这些都与病历结构无关，不必为病历引入动态分配。

> **发现**：`MiniCSV_ExportAllPatients`、`vMiniCSVTestTask`、`minicsvapp.o(.bss)` 在本版 map 里被链接器标为 `Removing`——说明当前**没有任何调用者**引用 CSV 导出，U 盘导出功能实际是"死代码"。若要保留"U 盘导出全量病历"，需要把导出接进某个可到达的入口（如 HMI 的保存键分支）。

## 4 写入顺序与掉电安全

FRAM（MB85RS512TPN）**字节可写、无需擦除、无页边界限制**，`epromWrite/epromRead` 支持任意长度（≤4 B 合并一条命令，>4 B 拆两次传输），没有擦写寿命问题（10^12 次量级）。

写入顺序刻意做成"先数据、后计数"，保证**掉电最坏情况是多出一条无效病历，而不是条数超过实际内容**：

| 操作 | 写入顺序 |
| --- | --- |
| 新增病历 `RecordAdd` | ① 写 12 B 病历到 `record[recordCount]` ② 写 `recordCount+1` |
| 插入病历 `RecordInsert` | ① 末位向前逐条后移 ② 写新病历 ③ `recordCount+1` |
| 删除病历 `RecordDelete` | ① 后续逐条前移 ② 末槽写 0xFF ③ `recordCount-1` |
| 新建患者 `PatientAdd` | 整块 144 B（memset 0 + 患者头）一次写入，覆盖槽位残留 |
| 删除患者 `PatientDelete` | ① 后续块逐块前移 ② 原末块整块写 0xFF |
| 清空 `treatmentEpromClear` | 32 B 分块把整区（55708 B）写 0xFF |

写放大：删第 1 个患者时最多搬 380 块 × 144 B ≈ 55 KB。SPI3 分频 2（PCLK1 42 MHz → 21 MHz），估算全表搬运 ≈ 20 ms 量级，按键操作的瞬时开销，可接受；FRAM 无磨损，不需要磨损均衡。

## 6 程序改造点

### 6.1 `MainApp/treatment.h` / `.c`（核心）

- 新类型 `treatmentRecord_t`(12 B)、`treatmentPatient_t`(144 B)，二者**只作 RAM 视图**；`treatmentLog_t` 降级为 RAM 会话。
- **落盘格式常量化**：新增 `RECORD_BYTES` / `HEAD_BYTES` / `PATIENT_BYTES` 与 `OFF_*` / `REC_OFF_*` 字节偏移常量；`RECORD_SIZE`/`PATIENT_SIZE`/`PATIENT_MAX` 全部改由这些常量推导，不再出现 `sizeof`。
- **字节编解码**：`treatmentRecordToBytes/FromBytes`、`treatmentPatientToBytes/FromBytes`、`treatmentPutU16/PutU32/GetU16/GetU32`（小端、逐字节）；所有 `epromRead/epromWrite` 只搬 `uint8_t` 缓冲，结构体不再直接进出 FRAM。
- 编译期护栏：结构体"装得进去"断言、格式自检 `#if`（偏移/对齐/1 字节 `recordCount`）、边界配置自检 `#if`、容量自检 `#error`。
- **新增应用级边界**：`PATIENT_LIMIT` / `RECORD_LIMIT` 宏 + 两个钳位读取接口 + 三处写入拦截。
- 地址计算统一 `treatmentEpromPatientAddr(i)`、`treatmentEpromRecordAddr(i, r)`（块内偏移 24 + r×12，全常量）。
- `treatmentEpromLoadPatientHeader()` 只读 24 B 头，各接口先读头再定位，减少无用读。
- 所有函数返回 `treatmentEpromErr_t`，入口做索引/指针校验，`PatientGet/Traverse` 把异常 `recordCount` 钳位到 ≤10。

### 6.2 `config/G5_TRI_A1_20260915/BoardConfig.h`（本次修改）

```c
// 扩容前
#define CONFIG_EPROM_TREATMENT_START  (CONFIG_EPROM_TREATMENT_END - (32L * 1536) + 1L)   // 15104
// 扩容后
#define CONFIG_EPROM_TREATMENT_START  (CONFIG_EPROM_BK_END + 37L)                          // 8548
```

- `+37` = BK 分区末尾（8511）+ 1 + 36 B（9 个分区 CRC），把 BK 与配置区之间的全部空隙划给病历。
- 上方 `TREATMENT_END`、`TREATMENT_SIZE` 保持表达式不变，`SIZE` 自动变成 55708。
- `BoardConfig.h` 自带的分区重叠自检继续生效：以后若再加分区 CRC 或挪动 BK，会直接 `#error` 拦住，不会静默写成越界地址。

## 7 界面交互（复用现有控件）

两种显示状态：

- **待保存会话**（`treatmentViewActive = 0`）：显示当前这次治疗参数，ID 栏 `NEW` 或 `0003(+)`；
- **浏览历史**（`treatmentViewActive = 1`）：显示已存病历，ID 栏 `0003  2/10`。

| 按键 | 行为 |
| --- | --- |
| 进入页面 | 复位浏览态，显示待保存会话 |
| `SAVETOUSB` | `patientId=0` → 新建患者并写首条；非 0 → 追加。成功后复位能量/时间/功率、`patientId=0`，跳到刚存的那条 |
| `LAST` | 上一条病历（扁平翻页）；未进浏览态时定位到**最新**一条 |
| `NEXT` | 下一条病历；未进浏览态时定位到**最早**一条 |
| `DELETE` | 删当前浏览那条；该患者清零时**连患者块一起删**（回收人数名额） |
| `INSERT` | **复诊**：追加到"会话指定患者 → 浏览病历所属患者 → 新建患者"的病历末尾，并回填 `patientId`（ID 栏变 `0003(+)`） |
| `CANCEL` | 清空会话（`patientId=0`） |

典型复诊流程：`LAST/NEXT` 翻到该患者任意一条 → `INSERT` → 追加第 N+1 条并停在那条。

已知交互缺口：页面没有"输入患者 ID 直接检索"的入口，只能翻页找人。要支持"输入 ID 一键带走"需在 `.tft` 加控件（或在 ID 框回车时触发 `treatmentEpromPatientFind`），本次未做。

## 8 兼容性与风险

| # | 风险 | 影响 | 现状/处置 |
| --- | --- | --- | --- |
| 1 | 存储格式不兼容 + 分区地址变更 | 旧机升级后旧记录被当成乱码患者块 | 按既有约定升级后整片清除（`CLEAR_EPROM_ALL` / `treatmentEpromClear`），不迁移 |
| 2 | `clearEprom(CLEAR_EPROM_TREATMENT)` 写 0x00 | 旧代码会读出 `id=0` 幽灵病历 | 新模型把 `patientId==0` 也判空块，已免疫；建议后续改调 `treatmentEpromClear()` |
| 3 | 不同编译器的结构体尺寸/对齐/枚举宽度 | 曾会让患者容量随之漂移、存量数据解析错位 | **已消除**：落盘字节与容量全部由常量+小端编解码决定，AC5/AC6/GCC 实测均 386 位；打包结构体（142 B）也不变（见 §2.5）。格式固化未改变字节内容，对既有数据兼容 |
| 4 | 分区改动后与旧固件/旧备份数据不通用 | 旧片子数据失效 | 升级流程已含整片清除；`BoardConfig.h` 自带重叠自检防误配 |
| 5 | 写放大（删患者前移最多 55 KB） | 几十毫秒耗时 | FRAM 无磨损；发生在按键回调，不阻塞激光控制 |
| 6 | 编解码多一层字节搬运 | 单条病历多几十个指令 | Code 由 195344 → 195752（+408 B），单条 12 B 开销可忽略；换来的容量与格式确定性更重要 |
| 6 | CSV 列结构变化 | 上位机/模板错位 | 需同步更新消费方，或改用新文件名 |
| 7 | 病历无日期时间戳 | 只能按写入顺序排序 | 需求未要求；需要时按 §3.4 加 4 B（患者 386→302） |
| 8 | 满 10 条策略 | 默认拒绝保存 | `CONFIG_EPROM_TREATMENT_OVERWRITE_OLDEST`；=1 则前移覆盖最旧 |
| 9 | 边界上限配置错误 | 写越界 | 编译期 `#if` 直接 `#error`；运行时 `treatmentEpromPatientLimit/RecordLimit()` 再钳位一次 |
| 10 | 患者块 144 B 栈帧 | 栈溢出 | mainApp 任务栈 24 KB，ZI 110800 B，余量充足 |

## 9 验证结论

### 9.1 实测（真编译器，非估算）

| 量 | 实测值 |
| --- | --- |
| 落盘患者块 `PATIENT_BYTES` | **144**（常量，非 sizeof） |
| 落盘单条病历 `RECORD_BYTES` | **12**（常量） |
| 病历数组偏移 `OFF_RECORD` | **24**（常量） |
| `sizeof(treatmentRecord_t)` / `sizeof(treatmentPatient_t)` | 12 / 144（RAM 视图） |
| `offsetof(treatmentPatient_t, record)` | 24 |
| `sizeof(treatmentLog_t)` | **36** |
| `CONFIG_EPROM_TREATMENT_SIZE` | **55708** |
| `CONFIG_EPROM_TREATMENT_START / END` | **8548 / 64255** |
| `CONFIG_EPROM_BK_END` | 8511（CRC 链 8512~8547） |
| `CONFIG_EPROM_TREATMENT_PATIENT_MAX` | **386** |
| `CONFIG_EPROM_TREATMENT_RECORD_MAX` | **3860** |
| `CONFIG_EPROM_TREATMENT_PATIENT_LIMIT / RECORD_LIMIT` | **386 / 10** |
| 尾部余量 | **124 B**（不足一个 144 B 块） |

跨编译器一致性见 §2.5（AC5 / AC6 / GCC / GCC 打包四组，患者数均为 386）。

### 9.2 构建验证

- 工具：Keil UV4 `-r`（全量重建）+ armcc V5.06 update 6 (build 750)
- 结果：**0 Error**；2 Warning 均来自第三方 `usbh_cdc.c`（`#225-D`，历史遗留，与本次无关）
- 产物：

```
Program Size: Code=195752  RO-data=8552  RW-data=1548  ZI-data=108492
FromELF: creating hex file...
MCU_Application.axf / .hex（约 575 KB）已生成
```

- 符号核对：`treatmentEpromPatientLimit`、`treatmentEpromRecordLimit`、`treatmentEpromRecordAdd` 均在最终镜像中可见。
- 踩坑记录：UV4 `-b` 增量构建会出现"源文件已改但目标文件不重编"的假象（日志里 symbol 未定义却看似通过），必须用 `-r` 全量重建核对；必要时先删对应 `.o`。

1. **时间戳**：每条病历加 `int32_t` 日期（块 184 B），患者 386→302，可按日期排序。
2. **块尾 CRC**：每块加 4 B CRC32（块 148 B），患者 386→376，可检出单块损坏。
3. **选患者入口**：病历页加"患者"控件或 ID 框回车触发 `treatmentEpromPatientFind`，需改 `.tft` 并重刷屏。
4. **统一清空语义**：`clearEprom(CLEAR_EPROM_TREATMENT)` 改调 `treatmentEpromClear()`（写 0xFF）。
5. **其它板型扩容**：6M3S / LYPE 按同一表达式扩满（各可得 186 → 更多），但需先核对该板分区布局。
6. **CSV 增强**：按患者聚合分段，或加"总条数/总能量"汇总行。
